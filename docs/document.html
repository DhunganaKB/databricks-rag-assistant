RAG Knowledge Assistant on Azure Databricks

A chat assistant that answers questions from company documents, cites every fact, and shows exactly where each cited passage sits in the source document: a box drawn on the PDF page or a highlighted span in a text file. It remembers the conversation and facts about the user in Databricks Lakebase, and it is deployed automatically from GitHub.

This guide covers the RAG application only. The ETL pipeline that prepares the documents (bronze → silver → gold) is documented separately; here it appears only as the source of the data the app reads.

2. Architecture

The app is a Python web service (FastAPI) running inside Databricks Apps, Databricks' managed hosting for web applications. Everything it talks to is a Databricks-managed service in the same workspace.

Databricks App

Hosts the web service and its user interface at a Databricks URL. It handles sign-in for you: only signed-in workspace users can reach the app, and the app learns who they are from a header Databricks adds. The app runs as its own service principal (see section 7).

Vector Search index

Holds every document chunk as a vector (meaning) plus its text (keywords). A hybrid query matches both, so "SEV2" or "401(k)" are found exactly while paraphrases are still understood. Every result also carries its citation location.

Model serving endpoints

Claude Sonnet 5.5 writes the answers. Claude Haiku 5.5, faster and cheaper, does the small jobs: rewriting follow-ups, titling chats, summarizing older turns, extracting memories.

SQL warehouse + volume

Used only by the source viewer: the warehouse looks up the boxes and page images of a citation, and the volume stores the page images the boxes are drawn on.

Lakebase

Databricks' managed PostgreSQL. It stores conversations, the running summary, long-term facts about each user, and feedback, with millisecond reads and writes. Nothing is stored on the app's machine.

GitHub Actions

Tests every change and, for changes merged to main, deploys the app and verifies the deployed version. It signs in as the deployment service principal sp-rag-deployer.

3. What happens when someone asks a question

One request to POST /api/chat. The logic lives in src/rag_app/agent.py; typical total time is 2–5 seconds.

  1. Identify the userDatabricks Apps adds the header X-Forwarded-Email after sign-in. The app takes the user identity only from this header, never from the request body, so nobody can pretend to be someone else.
  2. Load or create the conversationA new chat gets a new session_id. An existing one must belong to this user; anyone else's session id behaves as "not found".
  3. Protect against duplicatesEach message carries a client_message_id. If the browser retries after a network hiccup, the stored answer is returned instead of answering twice.
  4. Load memoryShort-term: the last 5 question/answer pairs word for word, plus a summary of anything older. Long-term: up to 10 facts the user shared in earlier conversations (e.g. "User is a contractor in the Rotterdam office.").
  5. Rewrite the follow-up"And in New York?" becomes "What is the hotel limit in New York?" using the conversation, so the search finds the right passages. The first question of a chat is used as is.
  6. Search the knowledge baseHybrid search returns 24 candidates. At most 4 chunks per document are kept (so one long document can't crowd out others), then the top 8 are numbered [1]…[8]. Temporary service errors are retried automatically.
  7. Write the answerClaude Sonnet receives the rules, the user's known facts, the conversation summary, the last 5 turns, and the numbered passages. The rules: use only the passages, cite every fact with [n], say so if the answer isn't there, and ignore instructions hidden inside documents.
  8. Attach the citationsEach [n] in the answer is mapped back to its passage, together with that passage's location: page boxes for PDFs, a character/line span for text files.
  9. Save the turnQuestion, answer, citations (with boxes), the rewritten query and timing are written to Lakebase in one transaction.
  10. Background housekeeping (after the answer is sent)Title the chat (first turn), fold turns that left the 5-turn window into the summary, and every 3 turns extract durable facts about the user. These never delay or break the answer.

4. Citations and bounding boxes

Every cited passage can be shown in its original place, and the location data travels with the answer.

PDF and Office documents: boxes

The ETL rendered each page as an image and recorded, for every chunk, rectangles (page, x0, y0, x1, y1) as fractions of the page width and height, with (0,0) at the top-left corner.

The viewer places transparent boxes over the page image using percentages (left = x0 × 100%), so they stay aligned at any screen size. A dashed box marks an estimated sub-region of a long paragraph.

Text documents: spans

Plain-text files have no page image, so the location is the exact character range [char_start, char_end) and line range in the stored document text.

The viewer shows the document and draws one box around that range, scrolled into view: the text equivalent of a page box.

"citations": [{
  "n": 1, "title": "Quarterly Business Review - Q3 2026", "section": "… > 2. Financial results",
  "doc_format": "paged", "pages": [1],
  "boxes": [{ "page": 1, "x0": 0.130, "y0": 0.296, "x1": 0.641, "y1": 0.447, "estimated": false }],
  "span": null
}]

Programs that aren't browsers can request the page with the boxes already drawn: GET /api/citations/{chunk_id}/pages/{page}/annotated.png.

5. Memory in Lakebase

All conversation data lives in Databricks. The deployed app uses its own database (rag_app), separate from local development (databricks_postgres).

Table (schema rag_memory)Memory typeContents
sessionsshort-termOne row per conversation: owner, title, number of turns, running summary of older turns
messagesshort-termEvery question and answer, with citations (including boxes), the rewritten search query and latency
user_memorieslong-termFacts a user stated about themselves (office, role, contract type, answer preferences), one row each
feedbackqualityThumbs up/down and comments per answer
schema_migrationsoperationsWhich database changes have been applied

Short-term memory (one conversation)

  • The last 5 question/answer pairs go to the model word for word.
  • When a turn falls out of that window, it is folded into a 150-word running summary.
  • From turn 7 on, the model therefore sees "summary of turns 1…n−5" plus "the last 5 turns", so long chats keep their context while the prompt stays small.

Long-term memory (across conversations)

  • Every 3 turns, the helper model extracts facts the user stated about themselves.
  • Sensitive information (health, religion, credentials, IDs, phone numbers, email addresses, salary…) is excluded twice: by the instructions and by a pattern filter.
  • Duplicates are rejected by the database itself.
  • Facts personalize answers, but company documents always win.
  • Users see and delete them under What do you remember about me?. Deletion is permanent.
Example from the live smoke test: in one chat the user said "I'm a contractor working in the Rotterdam office." In a brand-new chat, "Am I eligible for paid time off?" was answered with "Contractors are not eligible for paid time off under this policy [1]…".

6. The user interface

Left: conversations

New chat, the list of your previous chats (titled automatically), delete a chat, and What do you remember about me? to view or forget long-term memories.

Middle: chat

Answers with clickable [n] markers, the list of sources under each answer, how many history turns were used, the search actually run, and 👍/👎 feedback.

7. Service principals explained

A service principal is a non-human Databricks account: an identity for software instead of a person. It can be given exactly the permissions a program needs, and it appears in audit logs under its own name.

Why not use a personal account?

  • Continuity: a deployment that depends on a person breaks when their password changes, their session expires, or they leave.
  • Least privilege: a person usually has far more rights than a deployment needs. A service principal gets only what the job requires.
  • Accountability: audit logs show "the pipeline did this", not a person.

8. Setting up the deployment service principal

One-time steps, already completed for this environment. Labels show where each step happens: Databricks UI Terminal GitHub UI Automatic.

  1. Create the service principal Databricks UIUser icon → Settings → Identity and access → Service principals → Add new. Name sp-rag-deployer, type Databricks managed. Copy the Application ID. On Configurations, enable Workspace access only.
  2. Generate an OAuth secret Databricks UIOpen the service principal → Secrets → Generate secret. Leave Scopes empty (all APIs). A secret limited to e.g. access-management cannot deploy (see troubleshooting). Copy the secret; it's shown once.
  3. Grant data access SQL Editor 
    GRANT USE CATALOG ON CATALOG steampunk TO `79aa523d-36ef-4520-8623-855a5f92c5a8`;
GRANT USE SCHEMA, SELECT, MANAGE ON SCHEMA steampunk.dev_kbdhunga_rag_gold   TO `79aa523d-…`;
GRANT USE SCHEMA, READ VOLUME, MANAGE ON SCHEMA steampunk.dev_kbdhunga_rag_silver TO `79aa523d-…`;
    MANAGE lets the deployer pass read access on to the app's service principal. It cannot change the data.
  4. Grant the warehouse TerminalThe Serverless Starter Warehouse was created by the system and had no owner, so the UI refused changes. The fix was one full replacement (set) that made you owner, kept users → Can use, and added the deployer as Can manage: 
    databricks permissions set warehouses e21be0a5a64a99a6 --json '{"access_control_list": [
  {"user_name": "kbdhunga@mtu.edu", "permission_level": "IS_OWNER"},
  {"group_name": "users", "permission_level": "CAN_USE"},
  {"service_principal_name": "79aa523d-36ef-4520-8623-855a5f92c5a8", "permission_level": "CAN_MANAGE"}]}'
  5. Grant the Lakebase instance Terminal 
    databricks permissions update database-instances rag-memory-dev --json '{"access_control_list": [
  {"service_principal_name": "79aa523d-36ef-4520-8623-855a5f92c5a8", "permission_level": "CAN_MANAGE"}]}'
  6. Create the app's database TerminalAs the instance owner, from the repository folder: 
    uv run --env-file .env python scripts/post_deploy.py --instance rag-memory-dev --database rag_app \
    --bootstrap-for 79aa523d-36ef-4520-8623-855a5f92c5a8
    This creates database rag_app and lets the deployer create its tables there. The deployer then owns them.
  7. Store the credentials in GitHub GitHub UIRepository → Settings → Environments → dev: variables DATABRICKS_HOST and DATABRICKS_CLIENT_ID, secret DATABRICKS_CLIENT_SECRET. Deployment branches: main only.
  8. Everything else AutomaticThe pipeline creates the app, Databricks creates the app's service principal, and the pipeline grants it access and creates the memory tables. See section 12.

Someone impersonates another userIdentity comes only from the platform header set after Databricks sign-in

SQL injectionUser input reaches SQL only as bound parameters; configured table names are validated
Reading arbitrary filesPage images are served only from the configured page-image volume path
Malicious text in a document or answerThe UI inserts text safely (no HTML); the model is told passages are data, not instructions

The app changing its own database schemaThe app's role has data-only rights; only the pipeline applies schema changes
Storing sensitive personal factsSensitive categories are excluded from long-term memory; users can view and permanently delete memories

12. How GitHub Actions deploys the app

Three workflow files in .github/workflows/. A push to main (or Actions → deploy → Run workflow) runs the full chain; a pull request runs only the tests.

FileRuns whenDoes
ci.ymlpull requests, pushes to other branches, and as the first job of every deploymentLint, format check, 53 tests (fails below 80% coverage), check that requirements.txt matches the lock file
deploy.ymlpush to main, manual runRuns ci.yml, then _deploy.yml for environment dev
_deploy.ymlcalled by deploy.ymlThe deployment steps below
  1. PrepareCheck out the code, install uv and the locked dependencies, install the Databricks CLI (pinned version 1.22.1).
  2. Check configuration and identityFails with a clear message if a GitHub variable or the secret is missing; signs in and prints deploying as: 79aa523d-….
  3. Validate bundledatabricks bundle validate checks databricks.yml and resources/app.yml, and reads the resolved names (app, Lakebase, warehouse, schemas) for later steps.
  4. Deploy bundledatabricks bundle deploy uploads the code to the deployer's private folder and creates or updates the app, its resources and permissions. On the very first run, Databricks creates the app's service principal here.
  5. Grants and databasescripts/post_deploy.py (1) gives the app's service principal read access to the gold tables and volume in Unity Catalog, (2) applies pending Lakebase migrations, (3) gives the app data-only access to the memory tables, (4) verifies those grants.
  6. Deploy and start the appdatabricks bundle run installs requirements.txt in the app, starts it, and waits until it reports success.
  7. Smoke testscripts/smoke_test.py calls the live app as the pipeline identity. It runs a 7-turn conversation, checks memory, boxes and spans, the source viewer and idempotency, then deletes the data it created.
  8. Evaluation gatescripts/run_eval.py asks the live app 25 questions with known answers; a judge model grades them. The run fails below 90% correct. The report is attached to the run as eval-report-dev.
  9. SummaryThe run page shows the app URL, the commit and the evaluation result.
The deploy job uses the GitHub environment dev. Its secret is released only to that job and only on main. Two deployments never run at the same time, and a running deployment is never cancelled half-way.

14. Operating the app

TaskHow
Find the app in the UIApp switcher (grid icon, top right) → Databricks Apps. Clear the "Creator" filter: the app was created by sp-rag-deployer, not by you.
Ship a changeCommit, push to main, watch Actions → deploy. Ideally use a pull request first, so tests run before merging.
Read the app logsDatabricks Apps → rag-assistant-dev → Logs, or databricks apps logs rag-assistant-dev -p azure (needs an OAuth login: databricks auth login --profile azure; personal access tokens are rejected by Apps).
Change a settingEdit app.yaml (behavior) or databricks.yml (data, models, names, users) and push. Never edit the deployed app by hand: the next deployment would overwrite it.
Change the databaseAdd src/rag_app/store/migrations/002_<name>.sql. The pipeline applies it before the new version starts. Prefer additive changes (new columns) so the running version keeps working.
Roll backRevert the commit on main and push; the previous version is deployed as is.
Rotate the secretGenerate a new secret (scopes empty) on sp-rag-deployer, update DATABRICKS_CLIENT_SECRET in the GitHub environment, delete the old secret. Do this before the secret's expiry date (shown on the Secrets tab).
Save costStop the app when unused (Apps → Stop); the next deployment starts it again.
Correlate an errorEvery response carries an x-request-id, which appears in every log line for that request.

15. Local development

Run the same app on your laptop against the same Databricks services. It uses its own Lakebase database (databricks_postgres) and still stores nothing on the laptop.

make install                 # dependencies from uv.lock
scripts/bootstrap_env.sh     # create .env (git-ignored) with your token
make migrate                 # create/upgrade the local memory tables
make run                     # http://localhost:8000
make smoke                   # end-to-end checks against the local app
make check                   # lint + tests (what CI runs)
make eval                    # 25-question evaluation

18. Glossary

RAGRetrieval-augmented generation: find relevant passages first, then let the model answer from them.
ChunkA passage of a document (≈80 words on average here) that is searched and cited as a unit.
Hybrid searchSearch combining meaning (vector similarity) and exact words (keyword match).
Bounding boxA rectangle on a page image marking where a cited passage is.
Databricks AppA web application hosted and secured by Databricks.
Service principalA non-human Databricks account used by software.
OAuth secretThe password-like credential of a service principal; used with its Application ID.
Unity CatalogDatabricks' governance layer for tables, views, volumes and their permissions.
VolumeA governed folder of files in Unity Catalog (here: page images).
LakebaseDatabricks' managed PostgreSQL database.
Asset BundleFiles (databricks.yml + resources) that describe what to deploy, deployed with the Databricks CLI.
GitHub environmentA named set of variables and secrets in GitHub, released only to jobs that use it.
MigrationA versioned, ordered change to the database structure.
Smoke test / evaluation gateAutomatic checks of the deployed app; a failure stops the pipeline.
